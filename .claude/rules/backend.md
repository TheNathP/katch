# Backend rules (Supabase)

The backend is the only layer allowed to touch the database. Treat every request as coming from a decompiled, modified app.

## Structure

Supabase CLI commands run from `apps/backend/` (`pnpm exec supabase ...`) or via the root scripts (`pnpm db:start`, ...).

## Local vs production

- Develop and test against the **local stack** (`pnpm db:start`, Docker). CLI commands target local by default.
- The linked project is **production**. Never run commands that change it — `supabase db push`, `supabase functions deploy`, `supabase secrets set`, `supabase config push`, or anything with `--remote` / `--linked` that writes — without the developer explicitly asking. Read-only remote commands (`migration list --remote`, `functions list`) are fine. As with git, prefer handing the developer the command.

```
apps/backend/supabase/
├── config.toml                → local Supabase config (generated by the CLI, edit only what's needed)
├── migrations/<ts>_<name>.sql → schema, RLS, functions — created with `supabase migration new <name>`
├── seed.sql                   → local dev data
└── functions/
    ├── _shared/               → code shared between functions ("_" = not deployed as a function)
    │   ├── color/             → pure color logic: extraction, distance, scoring
    │   ├── db.ts              → Supabase client creation
    │   ├── auth.ts            → resolve the calling user from the JWT
    │   └── types.ts           → request/response types of every endpoint (source of truth for the API contract)
    └── <function-name>/       → one folder per endpoint, kebab-case (submit-photo/, get-daily-color/)
        └── index.ts
```

## Database

- Every schema change is a **new migration file**. Never edit a migration that has been merged to `main`; never change the DB through the dashboard.
- Every table: `enable row level security`, and **no policy granting `anon` or `authenticated` access** unless explicitly discussed. Edge Functions access data with the service role key, which only exists server-side.
- Table and column names: `snake_case`, plural tables (`games`, `attempts`).

## Edge Functions

Each function follows the same order:
1. Resolve the user from the `Authorization` JWT (`_shared/auth.ts`); reject with 401 if missing/invalid.
2. Validate the **whole** input against a schema (types, ranges, sizes, MIME type for images); reject with 400 on anything unexpected. Never trust IDs, timestamps, colors or scores sent by the client.
3. Check the user owns / is allowed to act on the resource (403 otherwise).
4. Do the work, return a typed response matching `_shared/types.ts`.

- **Scoring is server-only**: the target color is generated and stored server-side; the client uploads the photo; the function extracts the color, computes the score and persists it. The score algorithm lives in `_shared/color/` as pure functions, unit-testable without Supabase.
- Secrets (service role key, third-party keys) come from env (`Deno.env.get`) — never hard-coded, never returned in responses.
- Error responses don't leak internals (no SQL errors or stack traces to the client).
- The app has no access to backend code. When you change a request/response type in `_shared/types.ts`, update the mirror in `apps/mobile/src/data/api.types.ts` in the same change.
